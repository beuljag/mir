# MIR 버전 업로드 규칙

사용자가 2026-11-15에 지정한 규칙입니다.

- 기본 MIR 프로젝트 저장소: https://github.com/beuljag/mir.git
- 별도로 운영하는 HTML 서버 저장소: https://github.com/meuyeehug/mir.git
- 사용자가 특정 버전을 업로드해 달라고 요청하면 두 저장소 모두 업로드 대상으로 삼습니다. 각 저장소의 구조와 역할을 확인하고 해당 버전에 필요한 파일을 반영합니다.
- 브랜치를 만들어 올려 달라는 요청은 두 저장소에서 브랜치로 처리합니다. 그 요청만으로 main에 직접 반영하거나 병합하지 않습니다.
- PR을 요청하면 두 저장소의 변경에 대해 각각 PR을 만듭니다.
- 이 규칙 저장 요청 자체는 업로드·커밋·PR·병합·파일 삭제를 허가하는 요청이 아닙니다.
- V95와 현재 main 상태는 그대로 유지합니다. 앞서 요청했던 되돌리기는 취소되었습니다.

## 저장소별 업로드 범위

- `beuljag/mir`: 기본 MIR 프로젝트 저장소입니다. 사용자가 요청한 버전의 EXE 및 해당 프로젝트 파일을 반영합니다.
- `meuyeehug/mir`: MIR HTML 전용 저장소입니다. HTML, CSS, JavaScript, 이미지·문서 및 HTML 실행/서버 운영에 필요한 파일만 반영합니다.
- `meuyeehug/mir`에는 `.exe` 파일, Electron의 `main.js`·`preload.js` 등 데스크톱 전용 소스, Electron 의존성·설정, EXE 패키징·빌드·배포 파일을 넣지 않습니다. 파일 이름만으로 판단하지 말고 역할을 확인합니다.
- HTML 서버의 의존성·설정과 공용 브라우저 자산은 허용하지만, 데스크톱 전용 파일과 분리합니다.
- 이 범위 지정은 향후 업로드 규칙이며, 별도의 요청 없이 현재 원격 저장소 파일을 변경하거나 삭제하지 않습니다.

# MIR Railway 배포 호환성 및 지속적 개발 지침

## 1. 프로젝트 목표

MIR의 Windows 로컬 버전, EXE 버전, HTML 웹 버전, Railway 클라우드 버전이 동일한 소스 코드를 기반으로 정상 작동하도록 구성한다.

향후 기능 추가, UI 변경, 버전 업데이트가 발생해도 Railway 배포 호환성이 유지되어야 한다.

배포할 때마다 소스 코드를 수동으로 수정해야 하는 구조를 제거한다.

## 2. 현재 배포 환경

- GitHub 저장소: `meuyeehug/mir`
- 배포 브랜치: `main`
- Railway 프로젝트: `innovative-healing`
- 배포 환경: `production`
- OS: Linux

### 프론트엔드 서비스

- 서비스 이름: `mir`
- 실행 환경: Node.js
- Root Directory: `/`
- Start Command: `node serve.cjs`
- 기존 포트: `8791`
- 공개 주소: `https://mir-production-11d1117d.up.railway.app`

### 백엔드 서비스

- 서비스 이름: `calm-vibrancy`
- 실행 환경: Python, FastAPI, Uvicorn, MCP
- Root Directory: `/서버`
- Start Command: `python run.py`
- 기존 포트: `8000`
- Volume Mount Path: `/data`
- 공개 주소: `https://calm-vibrancy-production-07af9f2a.up.railway.app`

실제 소스 코드와 Railway 설정을 검사하여 위 정보와 달라진 부분이 있으면 변경 사항을 보고한다.

## 3. 핵심 개발 원칙

- Windows 로컬 실행 기능을 제거하지 않는다.
- EXE 및 Electron 실행 기능을 유지한다.
- Railway 호환 코드를 이전 버전으로 덮어쓰지 않는다.
- 클라우드 전용 기능과 로컬 전용 기능을 명확히 구분한다.
- 기존 UI, AI, MCP, DB, 회로 편집 기능을 유지한다.
- 기능 수정 전 기존 코드와 의존관계를 분석한다.
- 임시 우회 코드 대신 지속적으로 유지할 수 있는 구조를 구현한다.
- 기존 보안 검증을 무단으로 제거하지 않는다.

## 4. 실행 환경 자동 구분

`MIR_DEPLOYMENT` 환경 변수를 기반으로 로컬 환경과 Railway 환경을 구분한다.

- 미설정: 기존 로컬 실행 모드
- `railway`: 클라우드 실행 모드

클라우드 실행 시:

- HOST는 `0.0.0.0`을 사용한다.
- PORT는 Railway 환경 변수에서 읽는다.
- Windows 전용 명령어를 호출하지 않는다.
- 브라우저 자동 실행을 비활성화한다.
- 로컬 자동 인증 기능을 비활성화한다.
- localhost 고정 연결을 사용하지 않는다.
- HTTPS 원격 서버 연결을 지원한다.

로컬 실행 시 기존 동작을 보존한다.

## 5. Node.js 웹 서버 호환성

`serve.cjs`를 검사하고 다음 조건을 유지한다.

```javascript
const CLOUD = process.env.MIR_DEPLOYMENT === 'railway';

const PORT = Number(process.env.PORT || 8791);

const HOST = process.env.HOST ||
    (CLOUD ? '0.0.0.0' : '127.0.0.1');
```

기존 구현을 무조건 교체하지 말고 동일한 동작을 보장하도록 통합한다.

다음 환경 변수를 지원한다.

- `MIR_DEPLOYMENT`
- `MIR_WEB_ORIGIN`
- `MIR_BACKEND_URL`
- `HOST`
- `PORT`

필수 환경 변수가 누락된 경우 어떤 변수가 필요한지 명확히 출력한다. 비밀 값은 출력하지 않는다.

`ERR_INVALID_URL`과 같은 불명확한 오류만 남기지 않는다.

외부 요청은 승인된 백엔드 주소로만 전달한다. 임의의 외부 URL을 호출할 수 있도록 보안 제한을 제거하지 않는다.

Node.js 의존성과 실행 명령어를 package.json에서 관리한다.

## 6. Python 백엔드 호환성

`서버/run.py`, `서버/app/main.py` 및 관련 모듈을 검사한다.

Railway 모드에서는 다음 조건을 충족한다.

- `HOST`, `PORT` 환경 변수 지원
- Uvicorn 실행 지원
- Windows 전용 모듈 의존성 분리
- Linux 경로 및 UTF-8 파일명 지원
- 환경 변수 기반 API 인증
- HTTPS 및 CORS 지원
- MCP 연결 유지
- `/health` 상태 확인 API 유지
- 컨테이너 재시작 시 정상 복구

`requirements.txt`를 기준으로 Linux 호환 패키지를 설치한다.

`pywin32` 등 Windows 전용 패키지는 Windows에서만 설치되도록 조건을 유지한다.

KiCad, NGSpice가 필요한 기능은 Linux용 실행 파일과 의존성을 별도로 검사한다. 설치되지 않은 기능을 정상 작동한다고 표시하지 않는다.

## 7. AI 에이전트 및 커넥터

다음 환경 변수와 관련 코드의 의존관계를 검사한다.

- `COPILOT_DIRECT_LINE_SECRET`
- `COPILOT_DIRECT_LINE_DOMAIN`
- `COPILOT_CHAT_MODE`
- `OPENAI_API_KEY`
- `BRAVE_SEARCH_API_KEY`
- `CIRCUIT_API_KEY`
- `CIRCUIT_API_OWNER`
- `CIRCUIT_REVIEW_KEY`

실제 AI 공급자에 필요한 환경 변수만 필수로 지정한다.

친구 PC에서 실행되는 BAT 파일, Dev Tunnel 및 연결 프로그램의 역할을 분석한다.

Dev Tunnel이 단순한 외부 공개용이라면 Railway HTTPS 주소로 대체할 수 있는지 검토한다.

별도의 커넥터가 필요한 경우 Linux 호환 서비스로 분리할 수 있도록 설계한다.

실제 의존관계가 확인되기 전에는 불필요한 서비스를 생성하지 않는다.

친구 PC의 기존 서버와 Railway 서버를 임의로 혼용하거나 연결 주소를 강제 변경하지 않는다.

## 8. 데이터베이스 영구 저장

SQLite 데이터베이스는 Railway Volume에 저장한다.

```text
CIRCUIT_DB_PATH=/data/circuits.db
```

회로 데이터, 등록 부품, 검증 기록 및 기타 영구 저장이 필요한 데이터의 저장 위치를 검사한다.

- 재배포 후 데이터 유지
- 기존 데이터베이스 무단 초기화 금지
- 기존 Volume 삭제 금지
- 데이터베이스 스키마 변경 시 마이그레이션 적용
- 마이그레이션 전 백업 및 복구 방법 준비
- SQLite 동시 접근 및 다중 인스턴스 문제 검사

## 9. 보안 정책

실제 API 키와 인증 토큰은 Railway 백엔드 Variables에서만 관리한다.

필요한 비밀 변수에는 Sealed Variables 사용을 권장한다.

다음 항목에 실제 비밀 값을 저장하거나 노출하지 않는다.

- GitHub 저장소
- HTML
- 브라우저용 JavaScript
- API 응답
- 실행 로그
- Docker 이미지
- 배포 설정 파일
- 테스트 결과
- 개발 문서

`.gitignore`와 `.dockerignore`를 검사하고 다음 항목을 적절히 제외한다.

```gitignore
.env
.env.*
!.env.example

node_modules/
.venv/
venv/
__pycache__/
*.pyc
logs/

**/config/local-api-keys.json
**/config/local-review-key.json

*.db
*.db-wal
*.db-shm
```

기존에 Git으로 추적 중인 민감한 파일까지 별도로 검사한다. gitignore만 추가하면 이미 업로드된 파일이 제거되는 것은 아니다.

인증 정보가 노출된 경우 값을 재출력하지 말고 사용자에게 재발급 필요성을 보고한다.

## 10. Railway 배포 설정 관리

기존 두 Railway 서비스를 유지한다.

현재 Railway에서 지원하는 Infrastructure as Code 방식인 `.railway/railway.ts`를 검토한다.

기존 프로젝트 설정을 읽기 전용으로 확인하고 필요한 경우 가져온다.

실제 비밀 값은 설정 파일에 기록하지 않는다.

기존 서비스, 도메인, Volume, 환경 변수 및 자동 배포 설정을 보존한다.

설정 변경은 먼저 계획과 차이점을 검사한다. 삭제, 재생성 또는 운영 환경 변경은 사용자 승인 없이 적용하지 않는다.

기존 railway.json 및 railway.toml 사용 여부를 검사하고 최신 Railway 공식 문서에 맞게 처리한다.

Dockerfile이 필요한 경우 웹 서버와 백엔드 서버의 빌드 환경을 각각 구분한다.

GitHub main 브랜치에 push하면 Railway 자동 배포가 실행될 수 있음을 고려한다.

## 15. Railway 자동 연결 보안 정책 — 추가 지침 (2026-11-16)

사용자가 추가로 지정한 필수 정책입니다. Railway 자동 연결을 구현하거나 변경할 때 아래 항목을 함께 구현하고 검증합니다. 이 지침을 저장한 사실만으로 해당 기능이 구현·검증되었다고 보고하지 않습니다.

- 실제 API 키와 Copilot Direct Line Secret은 백엔드 환경 변수에서만 관리합니다.
- Railway Sealed Variables 사용을 고려합니다.
- API 키를 HTML, JavaScript, Electron 렌더러, 공개 API 응답 및 로그에 노출하지 않습니다.
- 사용자 로그인 및 세션 기반 인증을 구현합니다.
- 인증되지 않은 사용자가 서버에 저장된 관리자 API 키를 간접적으로 사용하지 못하게 합니다.
- 사용자별 데이터 접근 권한을 분리합니다.
- API 호출 횟수 제한과 사용량 제한을 구현합니다.
- 백엔드 주소 허용 목록 및 SSRF 방어 기능을 유지합니다.
- 기존 인증 기능을 제거하는 방식으로 자동 연결 문제를 해결하지 않습니다.
- 브라우저 개발자 도구, 네트워크 응답, 서버 로그, GitHub 소스 및 빌드 결과물에서 비밀 정보 노출 여부를 검사합니다.
- 자동 연결 기능과 보안 기능을 함께 테스트하고 검증 결과를 보고합니다.

기존 문서의 웹 API 키 직접 입력·전달 안내와 충돌하는 경우, Railway 자동 연결에는 이 추가 정책을 우선 적용합니다. 기존 백엔드 인증을 유지하면서 로그인·세션·사용자별 인가를 함께 적용해야 합니다. 비로그인·만료된 세션·다른 사용자 데이터 접근·호출 및 사용량 제한 초과·미승인 주소 요청이 거부되는지 검사하고, 미검증 항목은 명시합니다.

## 16. 서버 연결 시스템 구조 개선 지침 (2026-11-16)

사용자의 전체 추가 지침은 [docs/CONNECTION_SYSTEM_GUIDELINES.md](docs/CONNECTION_SYSTEM_GUIDELINES.md)에 보존한다. 연결 기능 작업 전에 이 문서와 15절의 보안 정책을 함께 확인한다.

- 기존 Node/Python/브라우저/MCP/Copilot/Electron 연결 모듈과 의존성을 분석한 뒤 변경 범위를 결정한다. 번들만 직접 고치지 않고 원본 수정 후 번들을 재생성한다.
- 공통 Connection Manager에서 환경·승인 주소·상태·로그인/세션·API·진단·재연결·해제·타임아웃·상태 감시를 관리하며 HTML/모바일/EXE에서 공통 로직을 사용한다.
- 사용자 로그인/세션과 서버 간 비밀 인증을 분리한다. HttpOnly/Secure/SameSite 쿠키, CSRF 방어, 만료/로그아웃, 사용자별 권한을 적용하며 관리자 키를 브라우저에 전달하거나 비로그인 사용자 대신 사용하지 않는다.
- 초기 5초, 점진 증가, 최대 60초를 기본으로 재시도하되 부하에 따라 조정한다. 인증 실패는 무한 재시도하지 않으며 중복 요청/세션을 방지하고 페이지 종료 시 정리한다.
- 웹/백엔드/인증/배선 DB/MCP/Copilot/검증 도구 상태를 분리하고 오류 단계 및 HTTP 상태·타임아웃을 구분해 알린다. 일부 실패로 정상 기능까지 막지 않는다.
- API 키 인증, 허용 목록/SSRF 방어, 사용자별 인가, 호출/사용량 제한을 유지하고 비밀 정보의 소스·로그·응답·빌드 노출을 검사한다.
- Railway MIR_BACKEND_URL 및 기존 환경 변수·두 서비스·Volume·DB를 보존한다. 프론트엔드 주소 고정이나 인증 제거로 해결하지 않는다.
- 자동 연결/복구/새로고침 세션/잘못된 인증/비로그인 AI·DB/DB 정상·AI 실패/MCP 복구/PC·모바일·EXE·Railway/비밀 노출/회로 편집 회귀를 함께 검사한다.
- 구조·사용법·자동 회귀 테스트를 문서화하고 미실행 검사는 미검증으로 보고한다. 사용자 승인 없이 main push 또는 Railway 운영 배포를 하지 않는다.

현재 요청은 지침 추가이다. 이 문서의 저장을 기능 구현·테스트 완료 또는 commit/push/운영 배포 승인으로 해석하지 않는다.


## 17. 현재 웹의 API 키 없는 사용 — 범위 정정 (2026-11-16)

사용자는 이번 작업에서 로그인·게스트 세션·호출 횟수 제한·사용량 제한을 새로 넣지 말고, 현재 웹사이트에서 API 키 입력 없이 사용할 수 있게만 수정하도록 명시했다. 이번 변경은 기존 공유 서버의 관리자가 이미 활성화한 `/mir/api` 공개 연결을 사용한다. 새 인증 구조나 관리자 키 대리 전달을 추가하지 않는다.

- Railway 웹은 MIR_BACKEND_URL로 승인된 동일 백엔드의 기존 공개 연결만 중계한다.
- 클라우드 웹에서 사용자 API 키를 요구하거나 전달하지 않는다. 백엔드의 공개 연결 거절도 우회하지 않는다.
- 기존 출처·승인 주소·경로·HTTPS·리디렉션 제한, 로컬/EXE 인증은 유지한다.
- 서버 주소·운영 변수·운영 서비스·Volume은 임의로 변경하지 않는다.
- 로그인/세션/호출 및 사용량 제한을 이번 변경에 추가하라는 과거 지침과 충돌할 때는 이 범위 정정을 우선한다. 그 밖의 비밀 노출 방지·기존 인증 보존 정책은 유지한다.
